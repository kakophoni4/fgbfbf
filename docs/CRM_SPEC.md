# Техническое задание: интеграция CRM с отдельным ИИ-сервисом

Версия: 1.1. Контракт ИИ-сервиса: 0.2.0. Обновлено после подключения серверов через WireGuard.

Документ предназначен команде разработки CRM. Он описывает работы в CRM; код ИИ-сервиса
развивается отдельно в https://github.com/kakophoni4/fgbfbf.

## 1. Цель и результат

Пользователь управляет ИИ из CRM без ручных команд на сервере после первоначального развёртывания.
Администратор настраивает подключение, промпт, каталог, проверяет ответы, загружает диалоги,
одобряет обучающие данные, запускает обучение, проверяет новую модель и активирует либо откатывает её.
Менеджер управляет участием ИИ в доступных ему чатах. ИИ консультирует до готовности клиента
заказать услугу, затем передаёт работу закреплённому менеджеру.

Смена промпта, изменение каталога и обучение — три самостоятельных операции. Нельзя называть
сохранение промпта обучением или показывать фиктивные этапы обучения.

## 2. Текущая готовность и условия запуска

Подтверждено на ИИ-сервере: API работает, /health отвечает, API видит установленную T-Pro в Ollama.
Код обучения опубликован, но полный цикл обучения/экспорта/активации не прошёл серверную приёмку.
GPU-worker запущен: /v1/training/status вернул worker_online=true и сведения о ресурсах.
Генерация через API ещё не подтверждена. Промпт должен задать администратор.

CRM и ИИ-сервис находятся на разных машинах. Соединение уже настроено и проверено:

- CRM: публичный IP 146.19.125.32, WireGuard IP 10.77.77.2, UDP 51821.
- ИИ: публичный IP 45.74.3.230, WireGuard IP 10.77.77.1, UDP 51820.
- Адрес API для backend/worker CRM: http://10.77.77.1:8088.
- GET /health вернул {"status":"ok"} как с хоста CRM, так и из контейнера crm-staging-api.
- На ИИ-хосте socat (fgbfbf-vpn-api.service) передаёт 10.77.77.1:8088 на 127.0.0.1:8088.
- Ollama остаётся на 127.0.0.1:11434 ИИ-хоста. Открывать её в интернет не требуется.

Повторно устанавливать VPN, Docker или ИИ API в рамках работ CRM не нужно.
Сетевое подключение worker CRM ещё проверить отдельно. /health не подтверждает правильность ключей.
Первый обязательный шаг команды — авторизованный запрос из api и worker CRM.

Последний замер: 6.36 GiB свободной GPU памяти, около 107 GiB RAM. Память GPU занимает также
отдельное обучение из /home/ml/src/ml-service; это не наш trainer. Эти числа — снимок,
актуальные получать через /v1/training/status. Не останавливать чужой процесс.
Профиль T-Pro требует 32 GiB свободной VRAM, T-Lite — 12 GiB; RTX 5060 Ti имеет всего 16 GB.
Наличие worker не означает возможность обучать T-Pro на этой карте.

Разработку интерфейса и клиента API можно вести сейчас. Автоответы реальным клиентам включаются
только после серверных проверок из раздела 19. Локальные запуски и тесты в этом проекте
заказчик не разрешил; выполнять проверку на выделенном серверном окружении.

## 3. Стек и границы ответственности

CRM: FastAPI, Python, SQLAlchemy AsyncSession, PostgreSQL, Alembic; Vue 3, TypeScript,
Vite, Naive UI, Pinia. Использовать существующие auth/RBAC, HTTP-клиент, уведомления,
очередь worker, websocket-события и механизм отправки сообщений. Не создавать вторую систему входа.

Команда CRM реализует:

- интерфейс и проверку прав;
- backend-клиент ИИ API и хранение секретов;
- историю чата, таймеры, состояние ИИ, защиту от гонок и отправку в канал;
- уведомление закреплённого менеджера;
- подготовку и обезличивание сырой CRM-выгрузки перед обучением;
- персональный аудит действий и связь идентификаторов CRM с объектами ИИ-сервиса.

ИИ-сервис отвечает за:

- общение с Ollama, системный контекст и структурированный ответ;
- хранение подключения, версий промптов, каталога, примеров и датасетов;
- очередь реального обучения, логи, артефакты и кандидаты моделей;
- активацию модели для последующих запросов и откат.

Браузер обращается только к backend CRM. Backend CRM обращается к ИИ API.
Нельзя обращаться из браузера непосредственно к Ollama, ИИ API или базе ИИ-сервиса.
Команда CRM не устанавливает PyTorch внутри CRM worker и не запускает обучение shell-командами.

## 4. Права доступа

Раздел «Управление ИИ» доступен только роли admin. Проверять роль на каждом backend-эндпоинте,
а также скрывать меню/защищать frontend-маршрут через существующие isAdmin/requiresAdmin.
Роли senior и group_senior сами по себе не дают права изменять промпты, модель или датасеты.

Управление ИИ конкретного чата доступно администратору и пользователю, который имеет право
обрабатывать этот чат по действующим правилам CRM. Это не даёт административный доступ к ИИ.
При передаче чата в другую группу/отдел доступ пересчитывается обычным механизмом CRM.

Менеджеру можно дать действие «Предложить исправление»: оно создаёт локальный черновик CRM,
но не одобряет обучающий пример. Окончательная проверка/одобрение — только администратор.

## 5. Два разных подключения

### 5.1. CRM → ИИ API

На backend CRM хранить:

- AI_SERVICE_BASE_URL — адрес отдельного FastAPI-сервиса, без /v1 в конце;
- AI_SERVICE_REPLY_KEY — запросы ответов/состояний;
- AI_SERVICE_ADMIN_KEY — операции управления;
- таймаут начального HTTP-запроса не менее 30 секунд;
- глобальный флаг разрешения автоматических ответов, по умолчанию выключен.

Для этой установки AI_SERVICE_BASE_URL должен быть ровно http://10.77.77.1:8088.
Значения ключей не приведены в ТЗ и не должны заменяться буквальным текстом в угловых скобках.
Заказчику дана команда подготовки файла /root/crm-ai-connection.env на ИИ-сервере.
Получить этот файл по защищённому каналу; если он ещё не создан, попросить владельца подготовить его.
Файл содержит три готовых присваивания: AI_SERVICE_BASE_URL, AI_SERVICE_REPLY_KEY,
AI_SERVICE_ADMIN_KEY. Не пересылать его в общий чат и не коммитить.

Команда CRM должна явно подключить эти значения к контейнерам api и worker через Compose
env_file либо environment. Просто положить файл на хост или выполнить присваивания в SSH
недостаточно: существующие контейнеры не получают новые переменные автоматически.
Учесть реальные Compose-файлы CRM: docker/docker-compose.staging.yaml и
deploy/server/docker-compose.vps.yaml, скрипт scripts/deploy/vps/update.sh.
Путь хранения файла и имена сервисов проверить в существующем Compose; не перезаписывать
основной .env CRM и не публиковать ключи через docker compose config.
Добавить только новые настройки и пересоздать затронутые api/worker штатным деплоем CRM.

Соответствие ключей: AI_REPLY_KEY из .env ИИ-сервиса становится AI_SERVICE_REPLY_KEY в CRM;
AI_ADMIN_KEY становится AI_SERVICE_ADMIN_KEY. Другие имена нужны только для разделения настроек.

Проверка после штатного деплоя CRM (Python-код выполняется внутри каждого контейнера api/worker):

```python
import json
import os
import urllib.request

base = os.environ["AI_SERVICE_BASE_URL"].rstrip("/")
opener = urllib.request.build_opener(urllib.request.ProxyHandler({}))
for path, key_name in [
    ("/v1/capabilities", "AI_SERVICE_REPLY_KEY"),
    ("/v1/connection", "AI_SERVICE_ADMIN_KEY"),
]:
    request = urllib.request.Request(
        base + path,
        headers={"Authorization": "Bearer " + os.environ[key_name]},
    )
    with opener.open(request, timeout=10) as response:
        result = json.load(response)
        print(path, response.status, result)
```

Ключи этот код не печатает. Успех — HTTP 200 на обеих операциях. Ошибка отсутствия переменной
означает, что Compose не передал настройки, 401 — неверный ключ, timeout — сетевой вопрос.
В приложении использовать общий асинхронный httpx-клиент, а не этот диагностический urllib-код.

Секреты — env/секретное хранилище CRM. Если предусмотрено изменение через админку,
использовать существующее зашифрованное хранилище секретов, показывать только «задан» и замену.
Не отдавать значения через GET и не включать в логи, Pinia, localStorage, экспорт настроек.

### 5.2. ИИ API → Ollama

В админке редактируются base_url и model через /v1/connection.
Для текущей установки Ollama на ИИ-хосте значение base_url может быть http://127.0.0.1:11434:
его использует ИИ-сервис, а не CRM. Не подменять его внешним URL самого API.

Показывать отдельные состояния: «API недоступен», «API доступен, Ollama не настроена»,
«Ollama недоступна», «Модель отсутствует», «Подключение проверено», «Генерация проверена».
configured=true означает только заполненные настройки. /health не проверяет модель.

## 6. Админский раздел «Управление ИИ»

Вкладки: «Подключение», «Промпты», «Каталог», «Тестовый чат», «Примеры», «Датасеты»,
«Обучение», «Версии моделей», «Журнал».

### 6.1. Подключение

Поля: URL Ollama, модель (список и ручной ввод), timeout_seconds, num_ctx, num_predict, temperature.
Кнопки: «Сохранить», «Получить модели», «Проверить подключение».
Использовать GET/PUT /v1/connection, GET /v1/models, POST /v1/connection/check.

PUT полностью заменяет настройки: всегда отправлять все поля из актуальной формы.
Не сбрасывать контекст и таймаут на значения по умолчанию при изменении только адреса.
Диапазоны: timeout_seconds 5–600; num_ctx 1024–32768; num_predict 32–2048; temperature 0–1.5.
Читать фактические настройки с сервиса. 16384 — желаемая стартовая настройка пользователя,
но не считать её установленной без ответа API. Расход памяти при увеличении окна проверяется на сервере.

Модель для ответов выбирается из уже установленных в Ollama. Кнопку скачивания не показывать:
такого эндпоинта сейчас нет. Ручную смену рабочей модели логировать отдельно от активации кандидата.

### 6.2. Промпты

Список версий: id, название, дата, признак активной. Просмотр полного текста.
Редактор создаёт новую версию, не меняет старую. Сохранение не активирует версию.
Действия: «Сохранить новую версию», «Проверить», «Активировать», «Вернуться к этой версии».
Откат промпта — обычная активация старого id. Тест не меняет активную версию.
Максимум title 120 символов, content 16000; обязательны непустые строки.

Показывать пояснение: сервис дополнительно добавляет обязательные правила формата ответа,
достоверности и допустимых сценариев. Редактор не является полным текстом всех системных правил.
При отсутствии активного промпта показать причину недоступности генерации и кнопку его создания.

### 6.3. Каталог

Редактор content, максимум 24000 символов, номер версии из GET /v1/catalog.
Сохранение через PUT /v1/catalog. Пустой каталог допустим, но ИИ не должен выдумывать услуги.
Включать актуальные услуги, результат, условия, цены, сроки, ограничения и случаи передачи менеджеру.
История версий каталога и откат каталога в текущем API отсутствуют: не рисовать неработающие кнопки.
Если CRM структурирует каталог карточками, backend формирует общий текст для этого API.

### 6.4. Тестовый чат

Выбор версии промпта, история теста, поле вопроса, отправка, очистка локальной истории теста.
Обычный тест через POST /v1/test/replies; тест модели-кандидата через соответствующий endpoint.
Показывать отдельно текст ответа и служебные поля action, reason, model, prompt_version,
catalog_version, request_id. Служебные поля не выводить в клиентский канал.

При 202 показывать ожидание и опрашивать состояние. Пользователь может закрыть вкладку:
задача и её идентификатор не теряются, после открытия статус восстанавливается через backend CRM.
«Очистить чат» не означает удаления истории в базе ИИ-сервиса; пояснить это в интерфейсе.
Тест никогда не вызывает существующую отправку сообщений реальному контакту.

### 6.5. Примеры

Из успешного ответа: «Сохранить как пример», редактор исправленного reply/action/reason,
поле note. Исходный source_request_id обязателен. Один пример на исходный запрос.
Список включает контекст, ответ, замечание, состояние проверки, даты.
Кнопки: «Редактировать», «Одобрить», «Удалить», «Экспорт одобренных».
После любого редактирования одобрение сбрасывается — обновить UI по ответу API.
Сообщение менеджера нельзя записывать как source_request_id несуществующей генерации:
для исторических диалогов использовать подготовку датасета из раздела 7.

## 7. Загрузка исторических диалогов и датасеты

Два входных пути: готовый JSONL/GZ по контракту сервиса и сырая выгрузка CRM.
Кнопки разделить: «Загрузить подготовленный датасет», «Подготовить из переписок CRM»,
«Собрать из одобренных примеров».

Готовый файл передавать backend-ом в POST /v1/datasets/import?name=... как бинарное тело,
НЕ multipart. До 32 MB загруженного и распакованного содержимого, до 10000 записей.
Если браузер отправляет multipart в CRM, CRM извлекает файл и проксирует его байты.
Декомпрессию и разбор сырого архива делать ограниченными по памяти/объёму в worker CRM.

Сырой архив вида {chat:..., messages:[...]} ИИ API напрямую не принимает. CRM должна:

1. Разобрать архив и показать найденные диалоги/ошибки без отправки их в обучение.
2. Упорядочить сообщения по времени и стабильному id; разделить разные обращения внутри чата,
   если это поддерживает существующая модель данных, сохранив общий chat_id для разбиения выборки.
3. Исключить тесты, /start, пустые сообщения, рассылки и технические уведомления.
4. Дать пользователю выбрать эталонные ответы; соседние сообщения менеджера можно объединить.
5. Вложения без извлечённого текста отметить, не считать их содержимое прочитанным.
6. Удалить или заменить персональные/платёжные данные, сохранив согласованность замен в диалоге.
7. Сформировать историю ДО выбранного ответа и сам эталонный ответ. Ответ не должен попадать в историю.
8. Показать предпросмотр и дать исправить system, историю, answer, action и reason.
9. После проверки сформировать канонический JSON и создать датасет.

Обезличивание — реальные преобразования и просмотр результата, а не только галочка.
Не переносить в обучение фиктивные сделки/вычеты, поддельные документы и закрытые данные без разрешения.

Каноническая запись:

```json
{
  "chat_id":"anonymous-chat-123",
  "system":"Инструкция и известные условия на момент эталонного ответа",
  "messages":[{"role":"user","content":"Можно подключиться удалённо?"}],
  "answer":{"reply":"Да, подключение удалённое.","action":"reply","reason":null}
}
```

POST /v1/datasets принимает {name, records:[...]}. JSONL содержит по одной такой записи на строку.
system обязателен: эталонный ответ должен иметь основания в контексте, а не угадывать цены из будущего.
История — только user/assistant, последняя роль user, максимум 50 сообщений на запись.
Отдельно есть экспорт примеров ИИ-сервиса с example_id/messages: импорт сервиса понимает его формат.

Датасет неизменяем после создания. Исправление — новая версия с новым id.
В интерфейсе показывать name/id/count, записи с пагинацией, duplicates_removed при создании,
approved и ошибки с номером строки. Минимум для запуска: 20 уникальных примеров, 5 разных chat_id.
Это минимальное условие программы, не гарантия качественной модели.

POST /v1/datasets/{id}/approve вызывается только после явного подтверждения пользователя:

```json
{"reviewed":true,"personal_data_removed":true,"authorized_services_only":true}
```

Не проставлять эти значения автоматически при загрузке. Поддержки изменения и удаления датасета
в API пока нет. Если требуется удаление/срок хранения, оформить отдельное требование владельцу ИИ API.

## 8. Обучение из CRM

Перед показом формы получать /v1/capabilities и /v1/training/status.
Если worker_online=false — «Обучающий сервер не подключён». Если ресурсов не хватает —
показать необходимый и доступный объём, не предлагать пользователю остановить рабочие ответы автоматически.
training_available=true означает только свежий heartbeat, не успешную проверку обучения.

Поля: dataset_id, base_model, epochs, max_length, learning_rate, seed.
base_model: t-tech/T-lite-it-2.1 или t-tech/T-pro-it-2.1 — исходные HF-модели, НЕ GGUF-имена Ollama.
Нельзя молча заменять T-Pro на T-Lite. Выбор делает администратор.
Параметры по умолчанию: epochs=1, max_length=1024, learning_rate=0.0001, seed=42.
Диапазоны: epochs 0.1–3, max_length 256–2048, learning_rate 0.000001–0.0003.
max_length обучения и num_ctx общения — разные настройки. Длинный обучающий пример не обрезается:
worker вернёт ошибку; пользователь должен сократить контекст или изменить допустимую длину.

POST /v1/training/jobs создаёт фоновую задачу и возвращает HTTP 202 с id/status.
Повторный клик блокировать. На timeout создания нельзя слепо повторять POST: проверить список задач
и сопоставить dataset/config/время, так как отдельного idempotency_key для обучения сейчас нет.

Список/карточка обучения: queued/running/succeeded/failed/cancelled, этап, step/total_steps,
числовые метрики, дата, ошибка, модель и датасет. Опрос worker CRM раз в 3–5 секунд только
для незавершённых задач; результаты доставлять frontend существующим websocket или polling.
Логи читать по after_id, сохранять next_after_id, не дублировать строки.
Не выдавать steps обучения за процент всего процесса: загрузка и экспорт имеют отдельные этапы.

«Отменить» вызывает /cancel, показывает «Отмена запрошена» и ждёт фактический cancelled.
Закрытие браузера не отменяет обучение. Обновление страницы восстанавливает состояние.
При worker_restarted задача failed, автоматического возобновления нет.
Новый запуск на расширенных данных обучает новый адаптер исходной модели, а не продолжает
произвольный предыдущий checkpoint. Предлагать полный накопленный проверенный набор.

## 9. Версии моделей

GET /v1/model-versions возвращает кандидатов после успешного экспорта.
Показывать model, id/job_id, endpoint, created_at, baseline_loss, candidate_loss,
train_examples, eval_examples и оценку человека. Loss — ошибка на отложенных примерах,
не процент качества. Отдельное поле evaluated в объекте версии означает одобрение человеком.
Не использовать metrics.quality_approved как актуальное состояние: это снимок на момент экспорта.

Последовательность действий:

1. «Проверить» → POST /v1/model-versions/{id}/test, тот же формат, что тестовый чат.
2. Администратор просматривает реальные ответы и сравнивает с рабочей моделью на одинаковых вопросах.
3. «Одобрить модель» → POST /v1/model-versions/{id}/approve, {quality_reviewed:true}.
4. «Активировать» → POST /v1/model-versions/{id}/activate; сохранить activation_id и previous_model в CRM.
5. «Откатить активацию» → POST /v1/model-activations/{activation_id}/rollback.

Идентификатор активации нужен для отката: сервис пока не имеет GET-списка активаций.
Не показывать активацию до получения положительного ответа. Конфликт 409 означает необходимость
обновить состояние, а не повторить операцию силой. Старые модели не удаляются.
Активную модель определять по GET /v1/connection.model, а не по дате последнего обучения.
Тест кандидата может вызвать переключение модели внутри Ollama и увеличить задержку обычных ответов.
Не выполнять массовое сравнение в пиковые часы без отдельного согласования ресурсов.

## 10. Поведение ИИ в реальном чате

В карточке чата показывать: режим, ожидание ответа, последнее действие ИИ, назначенного менеджера,
ошибку интеграции, включена ли 15-минутная подстраховка.
Кнопки: «Включить ИИ», «Передать менеджеру», «Выключить ИИ полностью».
Переключение не меняет владельца чата. История действий видна сотрудникам, не клиенту.

Рекомендуемые состояния CRM (это НЕ поля существующего ИИ API):

- OFF: никакой автоматической генерации, подстраховка тоже выключена.
- ASSISTANT: ИИ отвечает по входящим сообщениям, пока разрешено сценарием.
- MANAGER: основная работа у закреплённого менеджера; допускается отдельная подстраховка.

Дополнительный fallback_enabled управляет подстраховкой MANAGER. Глобальное выключение ИИ
подавляет все режимы, в том числе новые таймеры и отправку готовых результатов.
Внедрение начинается с OFF для существующих чатов, не включать всем автоматически.

При ASSISTANT система собирает последовательные сообщения клиента в один актуальный запрос.
Рекомендуется debounce около 2 секунд в worker, а не отдельная генерация на каждое слово.
История передаётся полностью в выбранных пределах: API не хранит разговор для автоматического
продолжения по chat_id. Сообщения сотрудников передаются как assistant, клиентов — user.
Не включать внутренние комментарии, ключи, служебные уведомления или нераспознанные вложения.
Если новый запрос состоит только из вложения, не имитировать понимание: направить человеку.

## 11. Передача менеджеру

Признаки готовности купить: явная просьба оформить, выставить счёт, согласие с предложенными
условиями. Вопрос о цене сам по себе не означает готовности.
action=handoff также означает вопрос вне компетенции, жалобу или прямую просьбу о человеке.
reason — произвольное внутреннее пояснение, не enum; не парсить его текст для критичных переходов.

При handoff CRM атомарно переводит чат в MANAGER, создаёт уведомление текущему закреплённому
менеджеру, записывает событие и прекращает обычные автоответы. Не создавать нового владельца
или случайный тикет, если по существующей логике он уже есть. Использовать текущий workflow CRM.
Если менеджер не назначен/недоступен для назначения, направить в существующую очередь отдела
и уведомить ответственного старшего; не терять запрос.

Текст клиенту берётся из reply только после проверки актуальности. Факт «уведомили менеджера»
сообщать только после успешного создания уведомления. Переход handoff не должен запускать
повторную генерацию, чтобы только перефразировать подтверждение.
Ответ менеджера переключает ASSISTANT в MANAGER и делает незавершённые ответы ИИ устаревшими.
Обычный режим ASSISTANT возвращается только явной кнопкой сотрудника с правом на чат.

## 12. Подстраховка через 15 минут

Работает только в MANAGER при fallback_enabled и разрешённых глобальных настройках.
Таймер начинается от первого входящего сообщения, на которое нет ответа человека.
Последующие сообщения не переносят срок. Всё отсчитывается backend/worker по UTC, не браузером.
Ответ человека отменяет ожидающую подстраховку. Закрытие/блокировка/удаление чата и OFF тоже отменяют её.

Через 15 минут CRM повторно проверяет актуальность и отправляет /v1/replies с mode=fallback.
ИИ отвечает по доступным данным либо возвращает handoff. Вне компетенции CRM фактически
уведомляет менеджера и может отправить нейтральное подтверждение без обещания срока.
context.manager_notified=true передавать только если уведомление действительно уже создано
для этого обращения; «прочитал» не выводить без отдельного подтверждения.

Не отправлять одно подтверждение каждые 15 минут. Для одного эпизода ожидания допускается
одна успешная подстраховка до ответа человека или явного включения ASSISTANT. Новое сообщение
в том же эпизоде не сбрасывает этот признак. Неуспешная генерация не считается отправленным ответом;
в таком случае уведомить сотрудника об ошибке, не запускать бесконечные повторы.

Если ответ сотрудника или новое сообщение клиента пришли во время генерации, результат устаревает.
При новом сообщении пересобрать запрос под новый id и тем же исходным сроком ожидания,
если подстраховка ещё не отправлена. При ответе сотрудника генерацию повторно не запускать.

## 13. Долгие запросы, гонки и доставка

request_id создавать на backend CRM и сохранять ДО HTTP-вызова. Использовать UUID или другой
глобально уникальный id, 8–128 символов [a-zA-Z0-9_.:-]. Тело запроса фиксировать для повторов.

POST /v1/replies возвращает 200 с результатом или 202/running примерно через 20 секунд.
При 202 worker опрашивает GET /v1/requests/{request_id} раз в 2–5 секунд до terminal status.
Для timeout/обрыва POST сначала искать результат по id; при 404 повторять ТО ЖЕ тело и id.
Запрос с тем же id и изменённым телом → idempotency_conflict; не создавать дубли вслепую.
Если исходный запрос failed, новая разрешённая попытка использует новый id, связанный с предыдущим.

Перед отправкой результата CRM в транзакции/под блокировкой проверяет:

- ИИ разрешён глобально и в чате;
- чат по-прежнему доступен, не закрыт и не заблокирован;
- не было ответа человека;
- не появилось более нового входящего сообщения;
- режим/ревизия управления ИИ не изменились;
- результат ещё не отправлен.

Нельзя держать транзакцию БД открытой во время HTTP-запроса к ИИ.
Ввести уникальность исходящей операции по ai_request_id. Использовать существующий outbox/очередь
отправки с идемпотентностью, чтобы сбой между записью в БД и отправкой в канал не создавал дубль.
Абсолютную exactly-once доставку во внешний канал без его поддержки не обещать; неопределённый
статус отправки разбирать штатным механизмом CRM, не повторять текст автоматически.

action=reply: отправить только непустой reply после проверок.
action=handoff: выполнить раздел 11 и при необходимости отправить reply.
action=no_reply: ничего не отправлять. reason сохранить внутри CRM.
Невалидный ответ/неизвестный action — ошибка интеграции и передача человеку, не сырой JSON клиенту.

Отмена ожидания в CRM не отменяет вычисление в ИИ API: endpoint отмены генерации пока отсутствует.
Помечать запрос obsolete и игнорировать поздний ответ. Отмена обучения — отдельная функция.

## 14. Данные на стороне CRM

Добавить миграции для состояния интеграции и связи запросов. Названия ниже рекомендуемые;
использовать существующие сущности там, где они уже решают задачу.

- ai_chat_state: chat_id, mode, fallback_enabled, revision, first_unanswered_at,
  fallback_sent_at, pending_request_id, updated_by/updated_at.
- ai_requests: request_id, chat_id, trigger_message_id, state_revision, mode,
  статус, время создания/завершения, snapshot входа либо его ссылка/хеш, result,
  model, prompt_version, catalog_version, причина obsolete/failed, исходящая операция.
- ai_training_links: внешний job_id, dataset_id, creator_user_id, последняя известная стадия.
- ai_model_activation_history: внешний activation_id, версия, previous_model, инициатор, дата.
- Черновики исправлений/подготовки датасетов и персональный журнал админских изменений.

Авторитетные версии промптов/примеры/обучение хранятся в ИИ-сервисе. Не создавать независимую
копию активной настройки, которая расходится с ним; локальные копии — только кеш/аудит.
Схему изменения настроек нескольких администраторов учитывать: сервис не предоставляет ETag.
CRM может сериализовать записи и предупреждать о конфликте локальной ревизии формы.

## 15. Обработка ошибок и ограничений

- 401 ИИ API: ошибка ключа интеграции; не разлогинивать CRM-пользователя как при истечении JWT.
- connection_not_configured / prompt_not_configured: показать действие настройки, не повторять автоматически.
- ollama_unreachable / ollama_timeout / ollama_http_error: показать недоступность, сохранить запрос,
  уведомить сотрудника, не сообщать клиенту выдуманный результат.
- context_budget_exceeded: сократить историю по явной политике; не терять молча важные условия.
- queue_full: ограниченный backoff, перед повтором проверить актуальность чата. API допускает
  одну генерацию и до восьми принятых запросов; CRM должна ограничить собственную очередь.
- model_invalid_answer: не отправлять JSON/обрывок; сохранить ошибку и передать человеку.
- trainer_offline / insufficient_resources / trainer_busy: объяснить конкретную причину.
- invalid_dataset_record: показать номер строки; ошибка не означает, что остальной файл одобрен.
- test_required / review_required: провести тест и одобрение до активации.
- endpoint_changed / activation_conflict / model_missing: обновить состояние, не обходить проверку.
- service_restarted / worker_restarted: отобразить failed, не рисовать продолжение процесса.

Во всех формах показывать реальные поля message/code, сохраняя локализацию CRM.
Общий формат: {error:{code,message,fields?}}. Не выводить пользователям traceback и секретные заголовки.
API имеет общий лимит 256 KB, импорт/создание датасета — 32 MB. Поднять соответствующий лимит
upload в proxy/CRM только для маршрутов загрузки, не для всех запросов.

Контекст ограничен ещё и консервативной проверкой по символам внутри сервиса: num_ctx не означает,
что можно отправить ровно столько символов истории сверх промпта. Ответ 422 нужно обрабатывать явно.
Память клиента, RAG, OCR/ASR и автоматическое резюмирование не входят в текущий API.

## 17. Безопасность, хранение, аудит

Ключи только на сервере CRM; между серверами приватный канал или HTTPS. Адреса для изменения
подключения доступны только admin. Не принимать внешний URL из пользовательского чата.
Не отправлять содержимое cookies, токены Telegram/WhatsApp, пароли и закрытые комментарии.
Фиксировать сотрудника, время, действие, объект и результат для изменений промпта/каталога,
одобрения примера/датасета, старта/отмены обучения, активации/отката и переключения чата.

ИИ-сервис хранит входящие запросы и контекст, автоматической очистки/обезличивания нет.
Удаление примера не удаляет исходную переписку. Команда должна согласовать срок хранения
и процедуру удаления до массовой загрузки реальных данных. Не обещать UI-кнопку полного удаления,
если backend ИИ-сервиса пока не поддерживает эту операцию.

## 18. Очерёдность реализации

1. Backend-клиент, секреты, права, сетевое подключение, отображение состояния.
2. Админские настройки, версии промпта, каталог, тестовый чат и polling.
3. Примеры и подготовка датасетов, загрузка и одобрение.
4. Интерфейс реальных задач обучения и версий моделей; проверка на GPU-сервере.
5. Интеграция реальных чатов, кнопки, handoff, 15-минутная подстраховка, защита от гонок.
6. Серверная приёмка, ограниченное включение, затем расширение после одобрения заказчика.

Разделы 1–4 можно разрабатывать без включения автоответов клиентам. Готовность админки
не означает готовность обучения или разрешение отвечать во всех чатах.

## 19. Критерии приёмки

Права и подключение:

- Не-admin не видит раздел и получает отказ при прямом вызове CRM endpoint управления.
- Менеджер не может переключить ИИ в чужом недоступном чате.
- В браузере/логах нет ключей ИИ API. Ошибка ключа не сбрасывает сессию CRM.
- API недоступен / Ollama не настроена / модель не найдена различаются в интерфейсе.

Промпты и генерация:

- Новая версия промпта сохраняется без активации; тестируетcя отдельно; активация и откат работают.
- Изменение URL не сбрасывает num_ctx, timeout и прочие параметры.
- Без промпта видна ошибка настройки; без каталога модель не получает выдуманный прайс от CRM.
- 200, 202, failed, обрыв POST и повторный id обработаны без двойной генерации/отправки.
- После перезагрузки вкладки сохраняются задачи и доступен результат.

Чаты:

- ASSISTANT отвечает только при разрешении и до handoff.
- Готовность купить передаётся закреплённому менеджеру, обычные автоответы прекращаются.
- Ответ человека во время генерации предотвращает отправку устаревшего ответа ИИ.
- Новое сообщение, OFF, закрытие чата и смена режима также блокируют устаревшую отправку.
- Таймер 15 минут не сбрасывается новыми сообщениями; ответ человека отменяет его.
- Одна подстраховка на эпизод; отсутствует повторное уведомление каждые 15 минут.
- Закрытый браузер не выключает таймеры. Два worker не отправляют один результат дважды.
- Вне компетенции фактически создаётся уведомление; нет ложного «менеджер прочитал».

Данные и обучение:

- Исправление одобренного примера сбрасывает его одобрение.
- Сырой архив проходит предпросмотр/подготовку, а не отправляется сразу в обучение.
- Повреждённый/слишком большой файл даёт понятную ошибку, не подвешивает worker.
- Датасет без одобрения не обучается; тип модели выбирается явно.
- Недостаточная GPU память показывается как недостаточная память, а не как «обучение запущено».
- На подходящей GPU проходит реальный цикл: задача → шаги → loss → новая модель в Ollama.
- Отмена и перезапуск worker дают реальные terminal статусы.
- Успешное обучение не меняет рабочую модель; тест/одобрение/активация выполняются отдельно.
- После активации новые запросы используют кандидат; откат возвращает предыдущую модель.
- До серверной приёмки не отображается утверждение «обучение проверено и готово».

## 20. Что передать по завершении работ CRM

Миграции, изменения backend/frontend, список переменных окружения, инструкция для администратора,
список созданных CRM endpoint, результаты серверных проверок с версиями CRM и ИИ API,
описание обработки гонок/повторов и оставшиеся ограничения. Отдельно указать адрес ИИ API,
факт проверки сети, промпта, генерации и полного обучения — без секретных ключей.
