# Реальное обучение через API — версия 0.2

Код обучения реализован, но по требованию заказчика НЕ запускался и НЕ тестировался локально.
До полного серверного прогона это кандидат к приёмке, а не проверенная production-функция.

## Разделение функций

Промпт/каталог меняются немедленно через обычный API. Обучение — отдельный Docker worker,
очередь и Python-процесс с Transformers/PEFT/bitsandbytes. Trainer получает только одобренный
неизменяемый снимок данных. Он не выполняет shell-команды из запросов, не останавливает Ollama,
не выгружает рабочую модель и не активирует результат автоматически.

Процесс: проверка свободной памяти → дедупликация → разделение по chat_id → токенизация без
обрезки → загрузка исходной HF-модели в NF4 → QLoRA (rank 8) → сравнение held-out loss →
сохранение адаптера → объединение на CPU с ТОЙ ЖЕ ревизией исходной модели → загрузка
safetensors в Ollama и квантование Q4_K_M → регистрация кандидата.

Baseline loss и candidate loss сравниваются на одном отложенном наборе. Никакой процент
«качества продаж» не выдумывается. Даже уменьшение loss не гарантирует качество общения:
перед активацией требуется реальный тестовый ответ и человеческое одобрение.

## Ресурсы

Профили первой реализации (порог допуска, а не обещание, что любая конфигурация поместится):

- T-lite-it-2.1 8B: минимум 12 GiB свободной GPU памяти, 40 GiB свободной RAM, 80 GiB диска.
- T-pro-it-2.1 32B: минимум 32 GiB свободной GPU памяти, 100 GiB свободной RAM, 260 GiB диска.

На RTX 5060 Ti 16 GB профиль T-Pro будет отклонён до запуска. Для него нужна другая GPU.
Профиль T-Lite не заменяет T-Pro молча: администратор явно выбирает base_model.
GPU 0 внутри контейнера — единственная используемая GPU. Другую физическую карту выбирают
через TRAINING_GPU_ID в Compose. Ограничения повторно проверяются worker перед стартом.
Совместное использование GPU с Ollama не гарантирует прежнюю скорость или свободную память.
Для сохранения производительности рабочей модели выделите отдельную GPU. Сервис НЕ освобождает
её остановкой ответов. При нехватке памяти обучение завершается ошибкой.
При импорте также нужен диск на стороне Ollama (если она удалённая — измерить отдельно).

## Однократное подключение worker на сервере

Нужен NVIDIA Container Toolkit и рабочий драйвер. Наличие nvidia-smi на хосте ещё не подтверждает
доступ GPU контейнеру. Настройка Toolkit может требовать перезапуска Docker; этот проект его
не выполняет автоматически. Согласовать отдельно, если на Docker работают другие сервисы.

Для текущего сервера с уже созданным compose.override.yaml (host network):

```bash
cd /opt/fgbfbf
git pull --ff-only origin main
docker compose up -d --build ai-api
docker compose -f compose.yaml -f compose.override.yaml -f compose.training.yaml up -d --build trainer
docker compose -f compose.yaml -f compose.override.yaml -f compose.training.yaml logs --tail=80 trainer
```

Первичная сборка скачивает большие CUDA/PyTorch пакеты. Исходные веса HF загружаются при первом
обучении и кэшируются в volume. API и worker должны использовать один ai-data volume на одном хосте.
Иная машина worker без общего volume этим вариантом не поддерживается. Сам Ollama endpoint
может находиться на другой машине. Не запускайте несколько workers/реплик.

```bash
set -a
. ./.env
set +a
API=http://127.0.0.1:8088
curl -sS "$API/v1/training/status" -H "Authorization: Bearer $AI_ADMIN_KEY"
```

Показывает worker_online, реальные свободные ресурсы и пороги профилей. capabilities сообщает
training_available=true только при свежем heartbeat. Это наличие worker, а не гарантия ресурсов
для конкретной модели. При недостатке ресурсов создание задачи возвращает 409.

## Датасеты

Все эндпоинты ниже требуют административный ключ. Нельзя автоматически одобрять сырую выгрузку.
Входящие переписки должны быть проверены по смыслу, обезличены и ограничены допустимыми услугами.
Эта версия проверяет структуру и требует подтверждения администратора; она НЕ выполняет
автоматическую юридическую экспертизу, очистку персональных данных или определение качества.

`POST /v1/datasets`:

```json
{
  "name":"Проверенные примеры",
  "records":[{
    "chat_id":"anonymous-chat-1",
    "system":"Ты помощник. Услуга ЭДО подключается удалённо. Верни JSON reply/action/reason.",
    "messages":[{"role":"user","content":"Нужно приезжать для подключения?"}],
    "answer":{"reply":"Нет, подключение проходит удалённо.","action":"reply","reason":null}
  }]
}
```

Ответ 201: id, count, approved=false, duplicates_removed. Максимум 10000 записей / 32 MB тела.
Для обучения нужно минимум 20 уникальных примеров из 5 разных диалогов. Это технический минимум,
не рекомендация по объёму хорошего датасета. После дедупликации минимум проверяется снова.

`POST /v1/datasets/import?name=...` принимает НЕ multipart, а бинарное тело JSONL или GZIP:
одна запись в указанном формате на строку. Принимается и JSONL экспорт /v1/examples/export.
Максимум 32 MB после распаковки. Ошибка формата возвращает номер строки, не её личные данные.

```bash
curl --fail-with-body -X POST "$API/v1/datasets/import?name=reviewed" \
  -H "Authorization: Bearer $AI_ADMIN_KEY" -H 'Content-Type: application/octet-stream' \
  --data-binary @reviewed.jsonl.gz
```

Сырая выгрузка CRM вида chat/messages с произвольными вложениями намеренно НЕ считается
готовым обучающим набором. CRM должна дать пользователю отобрать правильный ответ, контекст
и обезличить сведения. Файлы / фото / голос этим загрузчиком не расшифровываются.

- `POST /v1/datasets/from-approved?name=...` — снимок всех одобренных примеров сервиса.
- `GET /v1/datasets?limit=50&offset=0` — список.
- `GET /v1/datasets/{id}?limit=50&offset=0` — просмотр записей и count.
- `POST /v1/datasets/{id}/approve` с телом ниже — одобрение.

```json
{"reviewed":true,"personal_data_removed":true,"authorized_services_only":true}
```

Датасет после создания неизменяем. Исправления требуют новой версии датасета.

## Задачи обучения

`POST /v1/training/jobs`:

```json
{
  "dataset_id":"ID_ОДОБРЕННОГО_ДАТАСЕТА",
  "base_model":"t-tech/T-lite-it-2.1",
  "epochs":1,
  "max_length":1024,
  "learning_rate":0.0001,
  "seed":42
}
```

202: id/status=queued. Возможные состояния queued, running, succeeded, failed, cancelled.
Повторный POST при существующей активной задаче возвращает 409/trainer_busy.
На исправленных/дополненных данных новый запуск снова обучает адаптер исходной модели,
а не бесконтрольно продолжает предыдущий. Используйте полный накопленный проверенный набор.

- `GET /v1/training/jobs` — список с пагинацией limit/offset.
- `GET /v1/training/jobs/{id}` — config, status, metrics, error.
- `GET /v1/training/jobs/{id}/logs?after_id=0` — структурированные события и next_after_id.
- `POST /v1/training/jobs/{id}/cancel` — запрос отмены; дождаться cancelled.

Прогресс — настоящие stage и step/total_steps от Trainer. Для загрузки/импорта показывайте этап,
не выдуманный процент. Отмена останавливает дочерний процесс, а не Ollama. При импорте отмена
может оставить незарегистрированный артефакт в Ollama; он не активируется. После перезапуска
worker задача running помечается failed/worker_restarted, автоматического возобновления нет.
Логи модели/библиотек для диагностики остаются в закрытом volume /data/training/{id}/process.log.
API отдаёт только структурированные события. Автоматической очистки больших артефактов нет.

## Проверка, активация, откат

1. `GET /v1/model-versions` — кандидаты после успешного экспорта, model, endpoint, metrics.
2. `POST /v1/model-versions/{id}/test` — тело как /v1/test/replies. Получение результата через
   /v1/requests/{request_id}. Активную настройку не меняет. Промпт должен быть задан.
3. Прочитать несколько ответов, сравнить с исходной моделью на тех же вопросах.
4. `POST /v1/model-versions/{id}/approve` с `{"quality_reviewed":true}`. Без завершённого
   тестового ответа одобрение отклоняется.
5. `POST /v1/model-versions/{id}/activate` → model, previous_model, activation_id.
6. `POST /v1/model-activations/{activation_id}/rollback` → предыдущая модель. Если endpoint
   или активная модель уже изменены другим действием, возвращается 409, а не слепая перезапись.

Активация — смена model для НОВЫХ запросов. Запущенные обращения завершаются со своим снимком.
Старые модели не удаляются. Тест кандидата использует Ollama и её ресурсы: при MAX_LOADED_MODELS=1
Ollama может переключать загруженную модель, что увеличивает задержку. Планировать тесты отдельно.

## Приёмка на сервере

После установки выполнить полный цикл на проверенном наборе: загрузка → просмотр → одобрение →
обучение → фактические loss/артефакт → тест кандидата → одобрение → активация → откат.
Отдельно проверить insufficient_resources, отсутствие worker, отмену, слишком длинный пример,
неверный JSONL, запрет reply-ключу, restart worker и неизменность рабочего model до активации.
Без этого нельзя объявлять заказчику, что обучение прошло проверку и готово для всех пользователей.
