# Интеграция с CRM

## Общие правила

Все вызовы выполняет Python backend CRM. В браузер ключи ИИ-сервиса не передаются.
CRM проверяет свою сессию и роль admin до административного запроса.
Сервис не знает пользователей CRM: аудит фиксирует операцию под общим admin-ключом.
Персональный аудит «какой администратор изменил» ведётся дополнительно в CRM.

Заголовки: `Authorization: Bearer <key>`, `Content-Type: application/json`.
AI_REPLY_KEY: генерация, capabilities, состояние запросов.
AI_ADMIN_KEY: все операции. `/health` публичный, `/openapi.json` только admin.
Сервис предназначен для одной доверенной CRM, не для нескольких независимых арендаторов.

Ошибки: `{"error":{"code":"connection_not_configured","message":"..."}}`.
422: поля запроса или бюджет контекста; 401: ключ; 404: объект;
409: не настроено/конфликт/неуспешный повтор; 429: очередь заполнена;
502: Ollama недоступна/ошибка/неверный JSON; 504: таймаут; 503: обучающий worker не подключён.
Нельзя превращать ошибку API в утверждение «ваш запрос передан». CRM решает уведомление менеджера.

## Подключение

`GET /v1/connection` — сохранённые настройки, configured и gateway_token_configured.
configured означает наличие настроек, а не успешную связь.

`PUT /v1/connection` — полная замена настроек (пропущенные параметры получают значения по умолчанию):

```json
{
  "base_url": "http://10.0.0.10:11434",
  "model": "hf.co/t-tech/T-pro-it-2.1-GGUF:Q4_K_M",
  "timeout_seconds": 120,
  "num_ctx": 8192,
  "num_predict": 512,
  "temperature": 0.4
}
```

base_url — корневой адрес Ollama без /api, пароля, query и fragment.
Пустые base_url/model допустимы для сброса конфигурации; генерация тогда вернёт 409.
Входящий запрос не может переопределить адрес или модель.
`GET /v1/models` запрашивает /api/tags; достаточно сохранённого base_url.
`POST /v1/connection/check` проверяет связь и наличие модели, но не генерирует ответ.
Для проверки генерации используйте тестовый чат.

## Промпты и каталог

- `POST /v1/prompts` с `{"title":"Версия 1","content":"Инструкция..."}` → 201, объект с id.
- `GET /v1/prompts?limit=50&offset=0` → items, active_prompt_id.
- `GET /v1/prompts/{id}` → полный текст и дата.
- `POST /v1/prompts/{id}/activate` → active_prompt_id. Откат — тот же вызов со старым id.
- `GET /v1/catalog` → content, version.
- `PUT /v1/catalog` с `{"content":"Услуги, условия, цены..."}` → новая version.

Создание промпта НЕ активирует его. Редактирование — создание новой версии.
Смена активной версии действует на новые запросы; запущенные используют свой снимок.
Обязательные правила формата/достоверности добавляются сервисом отдельно от редактируемой инструкции.
Это не обучение параметров модели.

## Ответы

`POST /v1/replies`:

```json
{
  "request_id": "crm-123-message-456-v1",
  "chat_id": "123",
  "messages": [
    {"role":"user","content":"Можно подключить ЭДО удалённо?"}
  ],
  "mode": "assistant",
  "context": {"manager_notified":false}
}
```

messages содержит историю в правильном порядке; только user/assistant, последнее сообщение user.
Роль system не принимается от клиента: промпт задаёт администратор.
mode: assistant или fallback. fallback не запускает таймер; CRM передаёт его после своих 15 минут.
manager_notified=true только после фактического уведомления.
История не дополняется автоматически по chat_id: её всегда передаёт CRM.
request_id глобально уникален, 8–128 символов: латиница, цифры, `_ . : -`.

200:

```json
{
  "request_id":"crm-123-message-456-v1",
  "chat_id":"123",
  "reply":"Да, подключение удалённое. Какой системой ЭДО пользуетесь?",
  "action":"reply",
  "reason":null,
  "prompt_version":1,
  "catalog_version":1,
  "model":"hf.co/t-tech/T-pro-it-2.1-GGUF:Q4_K_M"
}
```

Если за 20 секунд результат не готов: HTTP 202 `{"request_id":"...","status":"running"}`.
CRM опрашивает `GET /v1/requests/{request_id}` раз в 2–5 секунд:

```json
{"request_id":"...","status":"succeeded","result":{"reply":"..."},"error":null}
```

result на самом деле содержит полный объект ответа выше. status: running/succeeded/failed.
При failed поле error содержит code/message. Общий таймаут CRM должен учитывать очередь до 8 запросов;
таймаут Ollama отсчитывается отдельно, когда начинается обработка.

Повтор того же тела с тем же request_id возвращает результат либо 202 без новой генерации.
Другой текст под прежним id → 409. Неуспешный id остаётся failed; для новой попытки нужен новый id.
После перезапуска незавершённые запросы помечаются failed/service_restarted. Автоповтора нет.
Смена каталога/настроек не изменяет сохранённый результат старого request_id.

action:

- reply: текст для возможной отправки;
- handoff: требуется менеджер, reason — внутреннее пояснение;
- no_reply: не отправлять, reply пустой.

Это решение модели, не гарантия. CRM должна повторно проверить актуальность чата перед отправкой.
Новые сообщения клиента, ответ менеджера или выключение ИИ могут сделать результат устаревшим.
CRM сопоставляет request_id с последним обработанным сообщением и сама исключает двойную отправку.

## Тест

`POST /v1/test/replies` — тот же запрос плюс необязательное `prompt_id`.
Без prompt_id используется активная версия. С ним можно проверить неактивную версию.
Тест не меняет активную модель и не отправляет ничего клиентам. Нужен admin-ключ.
История, исправления и результаты тестов хранятся так же, как обычные запросы.

## Примеры

`POST /v1/examples`:

```json
{
  "source_request_id":"crm-123-message-456-v1",
  "answer":{"reply":"Исправленный ответ","action":"reply","reason":null},
  "note":"Почему этот ответ лучше"
}
```

201 → `{"id":1,"approved":false}`. История, каталог и промпт берутся из исходного успешного запроса.
Это не автоматическое одобрение. Один пример на request_id.

- `GET /v1/examples?limit=50&offset=0` → items с messages, answer, note, approved.
- `PATCH /v1/examples/{id}` → answer и note, одобрение сбрасывается.
- `POST /v1/examples/{id}/approve` → approved=true.
- `DELETE /v1/examples/{id}` → 204.
- `GET /v1/examples/export?after_id=0&limit=500` → JSONL только одобренных примеров.

Для следующей страницы используйте X-Next-After-Id. Пустое тело означает конец.
Экспорт содержит example_id, chat_id, messages с точным системным контекстом и ответом в JSON-формате.
При подготовке обучения удалите служебные поля, обезличьте данные и разделяйте выборки по chat_id.
Экспорт не означает готовый проверенный датасет. Исходные диалоги сохраняются в requests даже при удалении примера.

`GET /v1/audit?limit=50&offset=0` — журнал изменений, без содержимого сообщений.

## Обучение

Обучение реализовано отдельным GPU-worker. Без свежего heartbeat capabilities возвращает
training_available=false, POST /v1/training/jobs — 503/trainer_offline. При нехватке памяти — 409.
Полный контракт датасетов, обучения, логов, кандидатов и отката: [TRAINING.md](TRAINING.md).
CRUD примеров и создание промпта сами по себе не являются дообучением.

## Задание команде CRM

Добавить админский экран: подключение, каталог, версии промпта, тестовый чат и проверенные примеры.
Показывать отсутствие настроек, ошибки сети, очередь и состояние запроса раздельно.
Для обучения показывать «Не подключено» по capabilities, не рисовать фиктивный прогресс.
Хранить ключи на backend. Для долгих запросов timeout исходного HTTP-вызова не менее 30 секунд,
далее опрос состояния. Таймеры, права на чат, handoff, кнопки и отправка остаются в CRM.
Эта версия API ничего автоматически не подключает к существующим чатам CRM.
